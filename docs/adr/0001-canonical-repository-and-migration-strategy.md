# ADR-0001 — المستودع الحاكم واستراتيجية الانتقال

- **الحالة:** Proposed
- **التاريخ:** 2026-10-19
- **القرار يخص:** SERS vNext

## السياق

يوجد مستودعان يحملان تاريخًا مهمًا للمشروع:

1. `anas8273/SERS`: تنفيذ قديم واسع مبني حول متجر القوالب والخدمات، Laravel/Next.js، ووثائق تاريخية.
2. `anas8273/sers-preview`: التنفيذ النشط الذي يحتوي Work Graph وEvidence/Asset وVersions وReviews وOutputs وفروع الوكلاء وPR11/PR12.

كما توجد وثائق تحليل وتصميم في Library لا تعيش كلها داخل GitHub. استمرار التطوير دون قرار حاكم يؤدي إلى:

- تكرار العمل.
- اختلاف الـstack والمخططات.
- دمج ميزات في المستودع الخطأ.
- ادعاء اكتمال غير قابل للتتبع.
- هجرة Big‑Bang عالية المخاطر.

## القرار

### 1. المستودع الحاكم

`anas8273/sers-preview` هو المستودع التنفيذي الحاكم لـSERS vNext.

`anas8273/SERS` يبقى أرشيفًا/مرجعًا تاريخيًا ومصدرًا انتقائيًا للأفكار أو الأجزاء، ولا يُعامل كمصدر حقيقة حالي.

### 2. الأسلوب المعماري

نعتمد:

> **Modular Monolith + Strangler Migration**

- Monolith منظم بحدود وحدات وعقود واضحة.
- لا Microservices مبكرة بلا ضرورة تشغيلية مثبتة.
- نقل الرحلات تدريجيًا من legacy إلى domain core.
- Feature Flags وAdapters أثناء الانتقال.
- لا حذف قبل backfill/reconciliation/rollback.

### 3. مصدر الحقيقة

- MySQL/العلاقات هي المصدر السلطوي للأعمال والملكية والعضويات والنسخ والمراجعات والاستحقاقات.
- الملفات في Object Storage خاص، مع metadata وchecksum وحالة فحص في DB.
- Search indexes وPDF وthumbnails وAI summaries بيانات مشتقة قابلة لإعادة البناء.
- لا قاعدة ثانية تصبح source of truth لنفس الكيان دون ADR جديد.

### 4. المستندات كمخرجات

- Work/Content/Assets/Version هي الحقيقة.
- PDF/Word/Link/QR Outputs مثبتة على WorkVersion.
- المخرج المعتمد لا يقرأ latest mutable state.

### 5. المتجر

- المتجر Bounded Context محفوظ.
- شراء المنتج يولد Entitlement، ولا ينقل ملكية محتوى المستخدم.
- المتجر ليس نقطة البدء الأساسية للـWorkspace ولا يحكم Domain Core.

### 6. الذكاء الاصطناعي

- AI خلف Gateway وعقود structured output.
- AI لا يصبح source of truth ولا يعتمد دليل تنفيذ دون تأكيد بشري.
- provider/model/prompt/version/cost/confidence قابلة للتتبع.

## البدائل المرفوضة

### أ. إعادة كتابة كاملة من الصفر

رُفضت لأن المشروع يحتوي نواة وعملًا وواجهات واختبارات قابلة للاستفادة، ولأنها تضاعف خطر فقد المتطلبات والانحدار.

### ب. الاستمرار فوق المسارات القديمة فقط

رُفض لأن ذلك يحافظ على تشتت الأدوات والمحررات والملكية والنسخ دون نموذج مجال موحد.

### ج. جعل المستودع القديم `SERS` هو الأساس

رُفض لأنه لا يحتوي آخر تنفيذ الوكلاء وPR11/PR12، ويمثل رؤية وتقنيات أقدم.

### د. Microservices من البداية

رُفض لزيادة التعقيد التشغيلي والمعاملات والتتبع قبل وجود حمل أو فرق مستقلة تبررها.

## النتائج الإيجابية

- مصدر واحد للحقيقة.
- الحفاظ على قيمة العمل السابق.
- انتقال قابل للعكس.
- سهولة تتبع المتطلبات والكود والاختبارات.
- إضافة أقسام فوق محركات مشتركة.
- منع تغيير المخرجات القديمة بصمت.

## النتائج السلبية/التكلفة

- فترة coexistence بين legacy وdomain.
- Adapters ومهام migration/reconciliation.
- الحاجة لاختبارات مضاعفة أثناء الانتقال.
- بعض الشاشات القديمة ستتوقف تدريجيًا بدل تحسينها مباشرة.
- يتطلب انضباطًا في Feature Flags وsource ownership.

## ضوابط التنفيذ

1. كل مسار legacy يحصل على قرار: keep/adapt/migrate/retire.
2. كل migration لها dry-run وإحصاءات وفشل قابل للاستعادة.
3. لا dual-write دائم.
4. لا public release لرحلة جديدة قبل policies وfailure tests.
5. كل Unit جديدة تستخدم المحركات المشتركة.
6. كل قرار يغير هذه الـADR يحتاج ADR superseding.

## خطة الانتقال الأولى

```text
Legacy ReportCenter
→ افتحه داخل Work
→ احفظ Content Blocks على الخادم
→ اربط Assets
→ أنشئ WorkVersion
→ Review على النسخة
→ Render Output من النسخة
→ Share/Revoke
→ أوقف حفظ المستند السلطوي في localStorage
```

- لا توجد تعليمات متعارضة في README/وثائق المشروع دون علامة Legacy.
